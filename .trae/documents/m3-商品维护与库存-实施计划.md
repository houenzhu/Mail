# M3 商品维护与库存 —— 实施计划

> **状态更新（2026-10-28）**：本文原始设计形成于 M3 开工前；批一“商品新增/编辑 + 分类品牌 CRUD”已在当前代码中实现，不能再把下方原始问题描述当作现状。批二“库存调整 + 库存流水”仍未实现。当前管理后台使用真实接口（`VITE_USE_MOCK=false`）。最新状态索引见根目录 README 和后端需求文档第 30 章。

## Context

M1（底座/登录）、M2（商品管理样板页）和 M3 批一已进入当前实现：商品新增、编辑（真实 SKU 回显与差量更新）、逻辑删除、上下架、分类与品牌的 CRUD 都有 BFF 和下游接口，前端页面也已接入。

当前仍未闭环的是库存管理：库存列表只是通过商品分页展示商品级库存汇总，不能按 SKU 分页；库存调整、`inventory_record` 流水分页与前端操作尚未实现。因此目前不能完成“建类目 → 发商品 → 改商品 → 调库存 → 查流水”的全链路。

M3 的目标是补全这条主线。按已确认的三项决策执行：

| 决策 | 结论 |
| :--- | :--- |
| 编辑商品时已有 SKU 的库存 | **编辑页不改库存**（已有 SKU 库存只读；仅新增 SKU 可填初始库存）。改库存统一走库存页并写流水，可审计、可对账，也避免商品事务里跨服务写库存 |
| 交付节奏 | **分两批**：批一 = 商品新增/编辑 + 分类品牌 CRUD；批二 = 库存调整 + 库存流水 |
| G-12 `product.sales` 回写 | **本轮不做**（列表"累计销量"列继续无写入方，属已知口径问题） |

## 关键设计决策

### 1. 保存商品的请求 DTO 放进 `mall-api`（共享契约）

Feign 的请求体类型必须**两端共享一份**，否则 BFF 与下游各持一份 record，字段一旦漂移就会出现"前端提交成功、下游字段为 null"这类静默故障——本项目已有的约定正是如此（`AdminProductPageQuery`、`DeductRequest` 等请求/响应 DTO 都在 `mall-api/com/zhe/mall/api/dto/`）。

因此：

- 新增 `mall-api` → `com.zhe.mall.api.dto.ProductSaveRequest` / `SkuSaveRequest`；
- **删除** `mall-product` 里的 `dto/ProductCreateRequest`、`dto/SkuCreateRequest`，改为引用 mall-api 版本；
- **新增与编辑共用一个 `ProductSaveRequest`**：`SkuSaveRequest.skuId` 为空 = 新 SKU，非空 = 已有 SKU。避免"create 一套 / update 一套"两份近乎重复的 DTO。

### 2. 编辑 = SKU 差量更新（diff），**不能整表重建**

`inventory.sku_id` 外键指向 `product_sku.id`，订单明细也引用 SKU。若编辑时"软删全部 SKU 再重新插入"，SKU 主键会变，**库存与历史订单全部对不上**。

因此 `ProductService.update` 按差量处理：

| 请求中的 SKU | 动作 |
| :--- | :--- |
| `skuId` 非空且属于本商品 | `updateBatch` 原地更新（主键不变，库存自然保留） |
| `skuId` 为空 | `insertBatch` + `initStock`（`stock > 0` 时） |
| 库中存在但请求中没有 | `softDeleteByIds` 软删除 |

### 3. SKU 编码唯一校验必须**排除自身**

`product_sku.uk_sku_code` 是全局唯一；现有 `countBySkuCode` 既不排除 `deleted`，也不排除自身。照搬会让"编辑商品但没改编码"直接报"编码已存在"。

→ 新增 `countBySkuCodeExcluding(skuCode, excludeSkuId)`；更新时对本商品已有 SKU 逐个排除自身，新增 SKU 则只排除请求内重复。

### 4. 库存"调整"拆成两个流水类型，保持 `qty` 恒为正

`inventory_record.qty` 的建表注释是**变动数量（正数）**，方向由 `type` 表达（1 扣减 / 2 回滚 / 3 预扣 / 4 预扣回滚）。手工调整如果是负数，就破坏了这个不变量，且 `uk_order_sku_type` 与对账口径都会含糊。

→ 新增 `ADJUST_IN(5,"调增")`、`ADJUST_OUT(6,"调减")`。前端只输入**带符号的增量**，后端按符号映射到 5/6 且 `qty = abs(delta)`。

同时修掉一处既有不一致：前端 `dict.js` 的 `INVENTORY_RECORD_TYPE_DICT` 现在写的是 `3=初始化 / 4=调整`，与后端枚举（`3=预扣 / 4=预扣回滚`）**完全对不上**，且 `init` 并不写流水。批二一并按后端真值对齐。

### 5. 分类/品牌删除要挡"被引用"

`product.category_id` / `brand_id` 是必填/常见引用。删掉在用类目会让商品落在"看不见的分类"上。

→ 删除前校验：分类**无子分类且无商品引用**、品牌**无商品引用**，否则拒绝并给出可读提示。

## 批一：商品新增/编辑 + 分类品牌 CRUD

> **当前状态：已落地。** 后端已有共享 `ProductSaveRequest`、商品新增/编辑/详情及 SKU 查询，分类/品牌写接口由 `mall-admin` 透传；管理页面已接入对应 API。下面保留最初的实现设计与验收要点作为决策记录。

### 后端 · mall-api（契约）

- 新增 `dto/ProductSaveRequest`（`name/subtitle/categoryId/brandId/mainImage/detail/status/skus`，沿用现有 `@NotBlank/@NotNull/@NotEmpty` 校验）、`dto/SkuSaveRequest`（`skuId/skuCode/name/specJson/price/marketPrice/image/stock`，注释写明 `stock` 仅新增时生效）。
- `ProductApi` 新增：`create`（`POST /admin`）、`update`（`PUT /{productId}`）、`skuByIds`（`POST /admin/sku-by-ids`，批二流水页用）。
  - 说明：BFF 经 `lb://mall-product` 直连，不受"网关只放行 GET `/api/product/**`"的限制，故下游写接口沿用 `/admin/**` 命名以保持隔离约定。

### 后端 · mall-product

**Mapper（`ProductMapper.xml` / `ProductSkuMapper.xml` + 接口）**

- `ProductMapper` 新增 `update(Product)`：只更新 `name/subtitle/category_id/brand_id/main_image/detail/status`（**不动** `sales / deleted / created_at`）。
- `ProductSkuMapper` 新增 `updateBatch(List<ProductSku>)`（按 `id` 更新 `sku_code/name/spec_json/price/market_price/image`）、`softDeleteByIds(List<Long>)`、`countBySkuCodeExcluding(skuCode, excludeSkuId)`。
- 复用已有：`updatePriceRange`、`selectByProductId`、`insertBatch`、`selectBySkuIds`。

**Service（`ProductService`）**

- `create(ProductSaveRequest)`：逻辑不变，仅替换 DTO 类型（现有实现已含 SKU 编码查重 + 库存初始化 + 缓存失效）。
- `update(Long productId, ProductSaveRequest)`（`@Transactional`）：按上文「决策 2」做 SKU diff；校验"至少保留一个未删除 SKU"；重算 `price_min/price_max` 调 `updatePriceRange`；商品主数据 `update`；最后 `evictProductCacheAfterCommit`（复用现有方法）。
- `skusByIds(List<Long>)`：复用 `productSkuMapper.selectBySkuIds`，给批二流水页用。

**Controller（`ProductController`）**

- `create` 改用 `ProductSaveRequest`；
- 新增 `@PutMapping("/{productId}") @RequireStaff(UserRole.OPERATOR) update(...)`。

### 后端 · mall-product（分类/品牌 CRUD）

- `Category`/`Brand` 实体已存在。Mapper 新增：`selectById`、`insert`、`update`、`softDelete`、`countByNameExcluding`、`countChildByParentId`、`countProductsByCategoryId`、`countProductsByBrandId`（后两者查 `product` 表）。
- 新增 `CategoryService` / `BrandService`：
  - 新增子分类时 `level = parent.level + 1`（`parentId = 0` → `level = 1`）；须校验父分类存在且未删除。
  - 名称唯一：分类在**同父下**唯一（对齐 `uk_parent_name`），品牌**全局**唯一（对齐 `uk_name`）。
  - 删除前按「决策 5」校验引用。
- `ProductController` 或新 Controller 暴露管理端端点：`POST/PUT/DELETE /api/product/admin/category`、`POST/PUT/DELETE /api/product/admin/brand`，写接口挂 `@RequireStaff(UserRole.OPERATOR)`。

### 后端 · mall-admin（BFF）

- `AdminProductService` 新增 `create`、`update`、`detail`（`getById` + `adminSkuBatch` 聚合出"商品 + SKU 列表"）。
- `AdminProductController` 新增 `POST /api/admin/product`、`PUT /api/admin/product/{productId}`、`GET /api/admin/product/{productId}`。
- `AdminCatalogController` 增补分类/品牌写端点，透传到下游。
- **角色校验继续只由下游 `@RequireStaff` 承担**，BFF 不重复判断（保持现有分层）。

### 前端

- `src/api/product.js` 新增：`createProduct`、`updateProduct`、`getProductDetail`、`createCategory/updateCategory/deleteCategory`、`createBrand/updateBrand/deleteBrand`。
- `ProductFormView.vue`：
  - `loadProduct` 改用 `getProductDetail`，回显**真实 SKU**，每个 SKU 行带 `skuId`；
  - 已有 SKU 的库存输入**禁用**并注明"库存请在「库存管理」中调整"；新增 SKU 可填初始库存；
  - `onSubmit` 按 `isEdit` 分流 `PUT /admin/product/{id}` 与 `POST /admin/product`；

- `CategoryListView.vue`：接线新增/编辑/删除（分类与品牌各一组），删除前二次确认并展示后端的拒绝原因。

## 批二：库存调整 + 库存流水

> **当前状态：未实现。** `mall-inventory` 目前没有 `adjust` 或流水分页 Controller/Service/Mapper；`mall-admin` 也没有对应 BFF 路由。库存列表仍复用商品分页的聚合汇总，调整/流水 UI 未接通。

### 后端 · mall-inventory

- `enums/InventoryRecordType` 新增 `ADJUST_IN(5,"调增")`、`ADJUST_OUT(6,"调减")`；同步 `sql/02_mall_inventory.sql` 中 `type` 列注释。
- `InventoryMapper` 新增 `adjust(skuId, delta)`：
  ```
  update inventory set total = total + #{delta}, available = available + #{delta}, version = version + 1
  where sku_id = #{skuId} and total + #{delta} >= locked and available + #{delta} >= 0
  ```
  （`locked` 不受影响；影响行数为 0 即"调整后总库存小于已锁定 / 会变成负库存"。）
- `InventoryRecordMapper` 新增 `selectPage` / `countPage`（按 `skuId`、`type`、时间范围筛选，`created_at desc`，复用 `idx_sku_created` / `idx_created`）。
- `InventoryService.adjust(AdjustStockRequest)`：复用现有 `tryClaim` / `replay` 幂等模式（`order_no` = 前端生成的 `requestId`，对齐建表注释"预扣场景可填 requestId"）；`delta == 0` 拒绝；失败写 `FAILED` 流水并回可读原因；成功后写 `SUCCESS`。
- `InventoryController` 新增 `POST /api/inventory/adjust`、`POST /api/inventory/record/page`。
- `mall-api`：`InventoryApi` 新增 `adjust` / `recordPage`，并新增 `AdjustStockRequest`、`InventoryRecordDTO`、`InventoryRecordPageQuery`、`InventoryRecordPage`。

### 后端 · mall-admin（BFF）

- `POST /api/admin/inventory/adjust` 透传下游。
- `POST /api/admin/inventory/record/page`：先取流水分页，再用 `ProductApi.skuByIds` 批量补 **SKU 编码 / SKU 名称**（跨库不能 JOIN，与现有"列表聚合库存"同一套路数；降级策略同现有实现——补名失败不影响流水本体）。

### 前端

- 新建 `src/api/inventory.js`：`adjustStock`、`pageInventoryRecords`。
- `InventoryListView.vue`：接上"调整库存"弹窗——输入带符号增量 + 备注，前端生成 `requestId`，成功后刷新并提示调整后库存。
- `InventoryRecordView.vue`：从占位换成真实分页表格（SKU 编码/名称、类型、数量、状态、备注、时间），带 SKU / 类型筛选。
- `constants/dict.js`：`INVENTORY_RECORD_TYPE_DICT` 按后端真值对齐为 `1 扣减 / 2 回滚 / 3 预扣 / 4 预扣回滚 / 5 调增 / 6 调减`。

## 验证方式

> 下列命令和用例是最初设计的验收方案，不是已经通过的记录。当前源码尚无库存调整实现，因此批二端到端验收无法执行；已有商品/目录测试与本计划列出的目标用例不是同一组。

1. **单测**（补在既有测试风格上，参考 `AdminProductServiceTest` 的桩写法）
   - mall-product：`update` 的 SKU diff（改/增/删各一）、SKU 编码冲突、至少一个 SKU、`price_min/max` 重算；分类删除的引用拦截。
   - mall-inventory：`adjust` 的幂等重放、`available` 不能为负、流水类型落到 5/6。
2. **构建**：`mvn -pl mall-api,mall-common,mall-product,mall-inventory,mall-admin install -B`（本地仓库在沙箱外，需 `dangerouslyDisableSandbox`）。
3. **真机端到端**（经网关 10000，operator01 令牌）
   - 发布商品 → `GET /api/admin/product/{id}` 回显 → `PUT` 编辑（改价 / 加 SKU / 删 SKU）→ 校验库存与 SKU 主键未变；
   - 分类/品牌 增改删，含"删除被引用类目应被拒绝"；
   - `POST /api/admin/inventory/adjust` 调增与调减 → 查流水分页能看到 type 5/6；
   - 用 `buyer01` 重放全部写接口，应全部 `403 / code 20003`（防越权回归）。
4. **前端**：`npm run dev`（5174）后走「发布商品 → 编辑 → 库存调整 → 流水」全流程；再跑 `node scripts/verify-login.mjs` 做登录回归。
   - 环境提醒：启动后端/前端进程需 `dangerouslyDisableSandbox: true`，否则进程会随命令结束被回收。
